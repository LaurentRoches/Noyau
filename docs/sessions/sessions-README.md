# Résumés de session

Un fichier par session de travail, `corebound-resume-session_NNN.md`, numéroté dans l'ordre chronologique.

## Ce qu'ils font autorité

`00-INDEX` §2 les place au **rang 2** de la hiérarchie d'autorité du projet, immédiatement derrière le code réel et devant `03`, `02` et `01`.

Cette autorité porte sur **l'état du code à la date de la session, et sur rien d'autre.**

## Ce sur quoi ils ne font pas autorité

**L'état actuel du projet.** Il vit dans les documents numérotés `00` à `07`, à la racine de `docs/`.

Un résumé n'est jamais amendé après coup : il est l'instantané d'un moment. Le résumé 003 décrit fidèlement le mois de juillet et ne décrit plus rien du code d'aujourd'hui. Lire un résumé ancien comme une description du présent est la même erreur que celle qui a rendu `game-design-notes.md` dangereux — ce document est resté figé sur la session 007-008 pendant que plusieurs fonctionnalités majeures étaient mergées, et il a été supprimé pour ça.

**La règle courte : pour savoir ce que le jeu fait aujourd'hui, lire `00` à `07`. Pour savoir quand et pourquoi une chose est devenue vraie, lire ici.**

## Ce qu'ils contiennent

Le format n'est pas figé. En pratique, chaque résumé rend compte de l'état du code à la clôture, des décisions prises pendant la session, des points laissés en suspens et des pièges rencontrés.

`06` §7.4 fait du résumé un livrable de clôture de session, au même titre que le texte de PR et la mise à jour du README.

## Rapport avec les autres documents

Quand un document du corpus écrit « vérifié le 8 septembre 2026 » ou « depuis la session 017 », c'est ici que se trouve la source. Ces renvois n'étaient pas résolvables tant que ce dossier restait hors du dépôt ; ils le sont depuis le 13 septembre 2026.
